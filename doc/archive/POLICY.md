# pakila 開発基本方針 (POLICY.md)

本プロジェクト『pakila』は、Rust 製インタプリタ `lasada` の機能を Lean 4 で完全再現し、数学的に証明可能な自律エージェントを構築することを目的とする。

## 1. 運用原則
* **文書先行原則 (Document-First)**: 全ての実装、修正、変更は、必ず事前にイシューファイル（`pakila/ISSUES/*.md`）への記載を行い、承認を得てから着手する。
* **ロードマップ禁止**: 実施計画はイシュー単位で管理し、個別のロードマップファイルは作成しない。
* **無断修正の厳禁**: 既存のファイルを上書き、簡略化、削除することは厳禁とする。既存の構造を神聖なものとして保持せよ。
* **証明義務**: 実装は形式証明を伴わなければ「未実装」と見なす。スタブ実装は一切認めない。
* **ドキュメントの言語**: 全てのドキュメントおよびコードコメントは日本語で記述すること。

## 2. 開発ワークフローとフェーズ定義

### Phase 0: 初期構築 (2026-06-01 完了)
* 基本アーキテクチャの確立、FFIの実装、UIのGemini CLI同期を main ブランチへの直接コミットで完遂。

### Phase 1: 継続的開発 (現在)
* **ブランチ運用の厳格化**: `main` (master) への直接コミットを禁止する。
* **フィーチャー開発**: 全ての新規機能、バグ修正は、`issue-` または `feature-` を冠した個別ブランチ（例: `git checkout -b issue-42-fix-inference`）で行う。
* **マージプロセス**: 個別ブランチでの実装およびテスト通過後、PR（プルリクエスト）形式でのレビューと承認を経て `main` へ統合する。
* **検証先行 (VFR)**: 修正前に必ず失敗するテストを作成し、修正後に成功することを証明するサイクルを徹底する。

## 3. 優先順位の哲学的指針 (Philosophical Prioritization)
本プロジェクトにおいて、UI/UX は単なる周辺機能ではなく、システムの生命線である（Class S）。ツールの価値は、その出力と人間との相互作用の質によってのみ定義される。したがって、形式証明とUIの洗練は不可分であり、UI/UX の実装・検証は、エンジン内部の論理基盤構築と同時に、あるいはそれ以上の優先度で遂行されなければならない。
