# イシュー: 実環境対話テストの Lean 4 ネイティブ化 (Formalized Environmental Testing)

## 概要
認証UI（AuthUI）などの「標準入出力・OS機能への依存」を伴う対話型インターフェースが正しく動作することを証明するために、使い捨ての Python スクリプト（pty 等）に依存せず、Lean 4 ネイティブな環境で実機同等のテストを行うための基盤設計。

## 背景と課題
- 「動作するとは実環境で動くこと」であるため、UI のレンダリングやブラウザ起動 (`xdg-open`) が実際に期待通りに行われるかを検証する必要がある。
- 現在、Lean 4 の標準ライブラリには `expect` コマンドや PTY（擬似端末）を直接操作する高度な抽象化が不足している。
- 恒久的なインフラとして Python を用いることはアーキテクチャの原則に反する。

## 解決方針 (戦略案)

いきなり実装に入らず、以下の段階的なアプローチで設計を行う。

### 1. 環境インターフェースの抽象化 (Environment Abstraction)
`IO.getStdin` や `IO.Process.spawn` を直接ハードコードするのではなく、副作用をカプセル化する型クラス（Trait）を導入する。これにより、テスト時には物理環境をシミュレートする「仮想物理環境」を注入可能にする。

```lean
class Environment (m : Type → Type) where
  readLine : m String
  printLine : String → m Unit
  spawnBrowser : String → m Unit
```

### 2. インタラクティブ・テスト DSL の構築
仮想物理環境に対して、「この出力が来たら、この入力を返す」というシナリオ（expect/send パターン）を記述できる Lean 4 上の DSL (ドメイン特化言語) を設計する。
これにより、Python スクリプトで行っていた E2E テストと同等のことを Lean の型チェックの恩恵を受けながら記述できるようにする。

### 3. C言語 FFI によるネイティブ PTY 操作 (オプション/長期)
どうしても「OS レベルでの PTY (擬似端末) の挙動」そのものをテストする必要がある場合は、現在 AVX-512 で使用している `native/kernels.c` を拡張し、`forkpty` や `ioctl` を Lean 4 に公開する FFI ラッパーを構築する。

## 次のステップ
まずは上記 1. と 2. の「抽象化とシミュレーション」の設計が、本プロジェクトにおける「実環境での動作証明」の基準を満たすかどうかの合意形成を行う。
